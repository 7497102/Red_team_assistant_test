# Тестовое задание: «Что улучшить в автомобильном ассистенте»

Индивидуальный проект для направления «анализ данных + веб-разработка».

## Задача продукта

У нас есть реальная история обращений к автомобильному голосовому ассистенту. Нужно сделать локальный веб-инструмент, с помощью которого продуктовая команда сможет ответить на два вопроса:

1. Какие задачи люди регулярно пытаются решить с помощью ассистента?
2. Какие сценарии стоит исследовать и улучшить в первую очередь?

Пользователь инструмента открывает вывод, видит масштаб наблюдения, проверяет исходные записи и понимает, какое изменение предлагается и как проверить его пользу.

## Формат работы

- До 8 часов индивидуальной работы и 30 минут защиты. По окончании времени сдайте достигнутый результат и список незавершённого.
- Стек и инструменты выбираете самостоятельно. ИИ разрешён, его использование не обязательно.
- Приложение запускается локально по вашей инструкции. Облачная инфраструктура и платные API для проверки задания не требуются.
- Все разработчики одной специализации получают один исходный файл, одинаковый лимит времени и одну шкалу оценки.

## Исходные данные

Файл `data/threadhistories_20pct_users.json`, 139 566 644 байт. Корневой объект содержит массив `threadhistories`.

В каждой записи есть `id`, `usersid_hash`, `role`, `text`, `actions`, `createdAt`, `updatedAt`, `deletedAt`, `timeSTT`, `timeCache`, `timeGPT`, `userLanguage`, `personality`, `type`, `internet`, `user_request_type`, `ai_response_type`, `stt_quality`, `ai_quality`.

Одна запись — одно сообщение или событие истории; количество записей не является количеством диалогов.

Контрольные характеристики предоставленной выборки:

|---|---:|
| Записи | 260 232 |
| Записи с `role=user` | 130 934 |
| Записи с `role=assistant` | 129 298 |
| Различные `id` | 260 232 |
| Различные значения `usersid_hash` | 999 |
| Минимальная дата `createdAt` | 2024-09-06 09:51:13 |

Дополнительный машинно-читаемый профиль находится в файле `data/dataset-profile.json`. Эти числа нужны для проверки корректности загрузки. Самостоятельное исследование требуется для содержательных выводов.

## Как подготовлены данные

Случайно выбраны **999 из 4995 значений `usersid_hash` — ровно 20% ключей**. Включены все имеющиеся записи выбранных ключей. Получилось **260 232 записей**, или **18.91% сообщений исходного массива**. Остальные записи не входят в пакет.

Это выборка целых групп, а не независимая 20%-ная выборка сообщений. Показатели относятся к выданной выборке. При обобщении необходимо учитывать различный объём историй и зависимость сообщений внутри одного ключа.

Корневая схема JSON и значения полей сохранены. Записи каждого `usersid_hash` расположены одним непрерывным блоком и отсортированы внутри по `createdAt`, затем по `id`. Такое расположение не создаёт подтверждённых границ диалогов. Индекс групп находится в `data/users-index.csv`; `first_record_index` — позиция первой записи группы в массиве с отсчётом от нуля. Seed случайного отбора: `20261105`.

Для всех обязательных требований ниже «весь корпус» означает весь предоставленный файл выборки. Дополнительная собственная выборка допустима только с явно обозначенной областью анализа.

## Обязательный результат

### 1. Воспроизводимая обработка

Сделайте импорт всего предоставленного файла выборки. Доступ к полному исходному массиву не требуется. Опишите команду запуска, хранение и фактическое время импорта. Повторный импорт того же файла не должен удваивать записи. Сохраните исходные `id` и используемые поля.

По умолчанию исследуется весь предоставленный исторический корпус, включая записи с заполненным `deletedAt`. В интерфейсе должен быть явный выбор: весь корпус / `deletedAt=null`. Это условие анализа архива; причины заполнения `deletedAt` неизвестны.

Покажите компактную сводку качества данных: объём, роли, даты, пропуски в используемых полях и обнаруженные ограничения. Не нужно строить отчёт по каждому столбцу.

### 2. Исследование потребностей и возможных проблем

Подготовьте две карточки исследования:

- Одну регулярно встречающуюся потребность пользователей.
- Одну проверенную гипотезу о возможной проблеме ассистента. Допускается обоснованное опровержение гипотезы или вывод, что данных недостаточно.

Кандидаты на исследование могут включать повторные просьбы, переформулировки, явное недовольство, пустые ответы или разрыв между намерением пользователя и ответом ассистента. Это примеры направлений, а не готовые выводы о корпусе.

Для каждой карточки нужны:

1. Наблюдение и точное правило отбора записей.
2. Число подходящих пользовательских сообщений и различных `usersid_hash`, участвующих в наблюдении. Если единица анализа другая — определить её отдельно.
3. Явная база расчёта: период, фильтры, знаменатель; полный корпус или выборка.
4. От трёх до пяти исходных примеров со ссылками по `id` внутри приложения.
5. Как минимум один неоднозначный пример или контрпример и описание его влияния на вывод.
6. Предлагаемое улучшение или следующий эксперимент, который позволит проверить гипотезу.

Метод группировки выбираете самостоятельно: правила, статистические методы, модели или сочетание подходов. Достаточно понятного метода с проверенными ограничениями. Не требуется автоматическая классификация каждой записи корпуса.

Если содержательный анализ делается на выборке, сохраните правило её получения и `id` выбранных записей. Нельзя выдавать частоты выборки за частоты всего корпуса. Проверьте, не упускает ли выбранный подход значительную часть обращений из-за языка; в метаданных много `uz-UZ` и `ru-RU`.

### 3. Веб-инструмент для проверки выводов

Минимальный путь пользователя: список карточек → карточка исследования → исходные записи и временной контекст.

Нужны:

- Поиск по тексту и переход к записи по `id`.
- Фильтры по периоду, роли, значению `userLanguage` и состоянию `deletedAt`.
- Отображение текущей области анализа и согласованных с ней счётчиков. При изменении фильтров приложение должно пересчитать показатели или явно оставить карточку в её исходной области анализа.
- Просмотр исходного текста, даты, роли, `actions` и полей, используемых в конкретном выводе.
- Возможность увидеть ближайшие по времени записи того же `usersid_hash`. Такой показ обозначается как временной контекст с описанным правилом, а не как подтверждённый диалог.

Интерфейс должен работать с подготовленной базой и выдавать ограниченные страницы результатов; не нужно передавать весь исходный JSON браузеру при открытии страницы.

## Границы интерпретации

- Полей `thread_id` и `session_id` в файле нет. Границы разговоров и соответствие конкретного запроса конкретному ответу нужно обосновывать; при неоднозначности её следует показывать.
- `usersid_hash` — наблюдаемый ключ. Его уникальные значения нельзя без дополнительной информации приравнять к различным людям или автомобилям.
- Ответ «сделано» и наличие кода в `actions` не подтверждают выполнение действия устройством. Значения кодов без отдельной документации могут оставаться гипотезой.
- Аудио и эталонных расшифровок нет. Независимо измерить качество распознавания речи по этому файлу нельзя.
- Происхождение, полнота и шкалы `stt_quality` и `ai_quality` неизвестны. Существующие метки следует исследовать до использования в качестве эталона.
- Единицы и смысл `timeSTT`, `timeCache`, `timeGPT`, а также часовой пояс дат не документированы в файле. Не представлять их интерпретацию как установленный факт и не складывать автоматически в сквозную задержку.
- Повторная просьба, пустая строка и слово недовольства — наблюдения или сигналы для проверки; сами по себе они не доказывают продуктовую ошибку.

## Что сдавать

1. Исходники, зависимости и инструкция локального запуска.
2. Команда импорта и необходимые скрипты обработки. Исходный большой JSON повторно прикладывать не нужно.
3. Работающий веб-интерфейс с двумя карточками и переходами к доказательствам.
4. Короткая записка: что установлено, что осталось гипотезой, что не успели, сколько времени потратили.
5. Если использовали ИИ: какие действия ему поручали и как проверяли существенные результаты. Достаточно конкретных примеров; полный журнал переписки не требуется.

## Приёмочные проверки

1. **Полнота и повторный импорт.** Предоставленный файл выборки даёт 260 232 записи. Повторный импорт сохраняет это число. Выбор `deletedAt=null` даёт 6 875 записей.
2. **Проверяемость карточки.** Проверяющий выбирает карточку и её примеры. По указанным `id` находятся те же исходные записи; правило отбора и область подсчёта воспроизводятся.
3. **Изменение области анализа.** Поиск и фильтры работают согласованно; пользователь видит, к какому периоду и набору записей относится показанное число. Показанная подборка не выдаётся за весь корпус.
4. **Защита от чрезмерного вывода.** Проверяющий выбирает неоднозначный случай. Разработчик объясняет альтернативную интерпретацию и показывает, что нужно для её проверки.

## Защита, 30 минут

- 5 минут: показать инструмент и главное содержательное наблюдение.
- 10 минут: воспроизвести один подсчёт, объяснить метод отбора и найти пример, ослабляющий вывод.
- 15 минут: исключить самый активный `usersid_hash` в области выбранной карточки, повторить расчёт и объяснить, изменился ли вывод. Это заранее объявленное небольшое изменение; готовый переключатель делать необязательно.

## Шкала оценки

| Критерий | Вес | Что служит доказательством |
|---|---:|---|
| Исследование и содержательная польза | 30% | Вопросы, гипотезы, альтернативные объяснения, обоснованный следующий шаг |
| Корректность и проверка | 30% | Воспроизводимые числа, ссылки на исходные записи, честные ограничения, проверка результатов ИИ |
| Веб-продукт и обработка данных | 25% | Полный импорт, работающий путь к доказательствам, согласованные фильтры, понятный запуск |
| Понимание решения на защите | 15% | Самостоятельное объяснение, повторение расчёта и работа с новой вводной |

Объём кода, число коммитов и количество сгенерированных ИИ страниц не являются отдельными критериями. Обоснованное опровержение гипотезы оценивается по качеству исследования.
